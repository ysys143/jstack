# 공공 조달 제안서 문체 분류 체계 v1.0 (Korean Public Procurement Proposal Taxonomy)

한국 공공기관 **조달 제안서**(공공 SI, 공공 정보화, 공공 용역) 작성 시 반복적으로 관찰되는 문체 일탈 패턴을 5개 대분류로 정리한다. `humanize-korean`의 taxonomy(A~J, AI 티 일반)와 **상호 보완적**으로 작동하며, 조달 제안서에만 고유한 `조달-확약 레지스터`의 이탈과 RFP 대응 형식 규정 위반을 포착한다.

## 적용 범위 (Scope)

- [O] 한국 공공기관(중앙부처·지자체·공공기관·국공립연구기관) RFP 대응 제안서
- [O] 기술·가격 협상 평가 대상 공공 SI/용역 제안서
- [O] 감리·검수 대응이 요구되는 조달 제안서
- [X] **학술 연구 제안서(grant / research proposal)** — 본 taxonomy 부적합. 연구-탐색 레지스터는 `~할 수 있다`, `~을 통해`, `가능성이 있다` 등이 본래 기능어이므로 O-1 처방을 적용하면 제안 취지가 손상됨. 학술 제안서는 `proposal-review` 스킬 사용.
- [X] 민간 기업 간 RFP 대응(B2B) — 본 taxonomy의 일부(M, N)만 적용 가능
- [X] 기술 보고서·학위 논문·정책 연구 보고서 — `humanize-korean` 사용

### 다른 제안서 장르와의 차이

| 장르 | 주요 레지스터 | 본 taxonomy 적용 | 권장 스킬 |
|---|---|---|---|
| 공공 조달 제안서 | 조달-확약(commissive) | [O] 직접 적용 | **public-procurement-style**(본 스킬) |
| 학술 연구 제안서 | 연구-탐색(investigative) | [X] 부적합 | `proposal-review` |
| 정책 연구 보고서 | 기술-분석(descriptive) | [X] M·N 선택만 | `humanize-korean` |
| 기업 백서·마케팅 문서 | 설득(promotional) | [X] 부적합 | `humanize-korean` |

## 심각도 기준 (humanize-korean v1.1과 동일)

- **S1 결정적(critical)**: 한 번만 나와도 감점 또는 형식 위반. 무조건 제거.
- **S2 강함(high)**: 1~2회 허용, 3회+ 반복 시 제거.
- **S3 약함(low)**: 다른 패턴과 중첩될 때 가독성 약화.

## 목차

K. 조달-확약 레지스터 이탈 (Register Deviation)
L. 요구사항 추적성 위상 붕괴 (Traceability Collapse)
M. 표·그림 캡션 형식 위반 (Caption Format Violation)
N. 본문-시각 자료 접합 붕괴 (Discourse Anchoring Failure)
O. 발주 규정 Hard Rule 위반 (Hard Rule Violation)

표기 규약: 본 문서는 다음 플레이스홀더를 사용한다. 실제 제안서에서는 해당 프로젝트의 RFP 체계·장번호 체계·명명 규칙에 맞추어 치환해 사용한다.

| 플레이스홀더 | 의미 | 치환 예 |
|---|---|---|
| `{REQ-ID}` | RFP 요구사항 식별자 | 프로젝트 고유 코드(예: `SFR-001`, `REQ-12`, `기능-3-1` 등) |
| `{CH}` | 장/절 번호 | 로마자·아라비아·한자·프로젝트 자체 체계 중 하나 |
| `{N}` | 장 내 순번 | 1, 2, 3, ... 또는 A, B, C |
| `{기능명}` | 시스템·모듈·기능 명칭 | `수집 체계`, `인증 모듈`, `품질 게이트` 등 |
| `{주제}` | 표/그림 주제 명사구 | `책임 경계`, `적용 표준`, `장애 복구 흐름` 등 |

## K. 조달-확약 레지스터 이탈 — S1~S2

공공 조달 제안서는 `확약(commissive speech act)` 레지스터를 기본값으로 삼지만, 표면 서법은 `개조식 보고서 문체(-임/함/됨)`로 제시하는 것이 권위적이다. 이 두 층위의 균형이 흔들릴 때 발생하는 패턴.

### K-1. `본 컨소시엄은` 절 서두 연속 노출 [S2]
- 패턴: 연속된 3개 이상 문단의 서두가 `본 컨소시엄은`으로 시작
- 예: 차별화 요소 N개 항목 모두가 `본 컨소시엄은 ~한다`로 개시
- 처방: 사태·구조·기능을 주어로 전환
  - `본 컨소시엄은 X를 Y로 설계한다` -> `X는 Y로 설계됨` 또는 `X 체계는 ~로 구성됨`
- 기준: 문서 전체 빈도보다 **연속 반복 구간**이 문제. 전역 빈도 30% 감축만으로 충분한 경우 많음

### K-2. `-한다`와 `-임/함/됨` 종결 혼재 [S1]
- 패턴: 동일 문단 내에서 확약형(`-한다/-이다`)과 개조식(`-함/-임/-됨`)이 규칙 없이 뒤섞임
- 예: "{기능명} 장애를 방지하는 방향으로 **설계함**. 구체 구현은 {패턴명}으로 **구현한다**."
- 처방: **절 단위로 서법 선택 고정**. 전략·확약 선언은 `-한다`, 구조 설명·목록 항목은 `-함/됨`. 같은 문단 안에서 혼용 금지
- 주의: 어느 하나로 **일률 통일**하는 것이 목표가 아님. 기능별 분리가 핵심

### K-3. 과장 수행문 [S3]
- 패턴: `반드시 준수한다`, `완벽히 이행한다`, `철저히 수행한다`
- 처방: 수식어 제거. `준수한다`, `이행한다`, `수행한다`로 단정

### K-4. `본 표는 ... 정리함` 메타 도입 반복 [S2]
- 패턴: 모든 표 앞 문장이 `본 표는 ~을 정리함` / `본 표는 ~을 요약함`
- 예: 한 절 안에 5개 표가 있고 각 표 앞이 전부 `본 표는 ~`
- 처방: 표의 필요성·맥락을 서술한 뒤 `~은 다음과 같다` / `~을 다음 [표 N]에 정리한다`로 연결. §N-2 참조

### K-5. 1인칭 복수 `우리`·`우리 회사` 사용 [S1]
- 패턴: `우리는`, `우리 회사`, `저희는` 등 구어체 1인칭
- 처방: `본 컨소시엄`, `본 사업`으로 치환. 단 K-1과 동시에 걸리면 K-1 우선

## L. 요구사항 추적성 위상 붕괴 — S1~S2

RFP 요구사항 ID(예: SFR/PER/CNR/DAR/SER/PMR 계열, 또는 해당 사업의 자체 코드 체계)는 `요구 조항`이지 `설계/구현 산출물`이 아니다. 두 위상을 혼동하면 텍스트가 무너진다.

### L-1. 요구사항 ID를 설계/구현 주어로 사용 [S1]
- 패턴: `{REQ-ID}은 ~로 설계됨` / `{REQ-ID}은 ~로 구현됨`
- 문제: 요구사항 ID는 RFP가 선언한 요구 조항이지 본 사업의 산출물이 아님. 설계되는 것은 `{기능명}`·`{모듈명}`
- 처방: **부사절 격하 + 기능 단위 주어**
  ```
  [전] {REQ-ID}은 이중 구조로 설계됨.
  [후] {REQ-ID} 요구사항에 대응하여, {기능명}은 이중 구조로 설계됨.
  또는
  [후] {기능명}({REQ-ID})은 이중 구조로 설계됨.
  ```

### L-2. 요구사항 ID와 기능명 접착 주어 [S2]
- 패턴: `{REQ-ID} {기능명}은 ~을 수행한다`처럼 ID와 기능명을 공백만으로 붙여 주어 덩어리로 사용
- 처방: ID를 괄호로 격하하거나 부사절로 처리
  - `{REQ-ID} {기능명}은 ~` -> `{기능명}({REQ-ID})은 ~`

### L-3. Canonical sentence 노출 과다 [S3]
- 패턴: 여러 파일에서 동일 정의 문장(경계 정의문, 핵심 원칙 선언)을 복사해 반복. 문서별 맥락 없이 선언만 반복
- 처방: canonical sentence 앞뒤로 `왜 이 정의가 필요한지` 설명 문장과 `적용 범위` 해설을 덧붙여 `정의 조항 + 보고서 산문`의 결합 형태로 재구성

### L-4. `본 {REQ-ID}은` 주어화 [S2]
- 패턴: `본 {REQ-ID}은 ~의 출발점이다`처럼 ID 자체를 주어로
- 처방: `본 {REQ-ID}이 요구하는 {기능명}은 ~의 출발점이다` 또는 해당 기능명을 직접 주어로

## M. 표·그림 캡션 형식 위반 — S1~S2

대규모 참고제안서 표본에서 귀납한 캡션 통사 규칙. 구체 수치·헤드노운 집합은 `caption-headnouns.md` 참조.

### M-1. 캡션 bold 감싸기 누락 [S1]
- 패턴: `[표 {CH}-1] ~` (bold `**` 없음)
- 처방: 전수 `**[표 {CH}-1] ~**` 형식으로 통일
- 근거: 우수 참고제안서군에서 표 캡션의 bold 처리 비율은 약 90% 이상 — bold는 `시각 단절(visual segmentation)` 신호로 기능

### M-2. 헤드노운 집합 외 종결 [S1]
- 패턴: 캡션 끝 어절이 표 헤드노운 13개 닫힌 집합 밖
- 집합 밖 예: `근거`, `발췌`, `6종`, `하이라이트`, 파일 확장자/기술 약어 종결
- 처방: 대응 헤드노운으로 교체. 닫힌 집합은 `caption-headnouns.md` 참조.

### M-3. 번호 체계 3단 이상 혼재 [S2]
- 패턴: 동일 문서에 `[표 {CH}-{N}.{N}-{N}]` 3단, `[표 {CH}-{N}]` 2단, 번호 없는 `[표]` 등 복수 형식 공존
- 처방: 전 문서에서 `[표 {장}-{번호}]` 2단 하나로 고정. 보충표만 `[표 {장}-{번호}A]` 허용

### M-4. 캡션 직후 조사 연결(경계 와해) [S1]
- 패턴: `**[표 {CH}-N] 주제 헤드노운**는 ~이다.` — bold 닫힘 후 조사 `~는`이 붙어 캡션이 문장 주어로 흡수
- 처방: 캡션과 본문을 **별도 문단**으로 분리. 캡션 다음 줄에 빈 줄 1개 후 설명 문단 시작

### M-5. 캡션 길이 초과 [S2]
- 기준: 표 캡션 평균 5어절 이하 권장, 7어절 초과 금지, 10어절 이상은 강제 분할
- 처방: 명사구 중심으로 압축. 부가 설명은 캡션 앞뒤 본문으로 이동.

### M-6. 번호 없는 캡션 [S1]
- 패턴: `**표 — 주제**` / `**주제 테이블**` (번호 부재)
- 처방: `**[표 {장}-{번호}] 주제 헤드노운**` 형식 복구

### M-7. 종결어미 캡션 [S1]
- 패턴: `[표 N] ~이다` / `[표 N] ~한다`
- 처방: 무어미 명사구로 변환. 캡션은 본문의 음슴체와 대립하는 `무어미` 상태여야 서법 대립 기능

## N. 본문-시각 자료 접합 붕괴 — S1~S2

우수 참고제안서는 모든 시각 자료를 `도입 텍스트 -> 시각 자료 -> 해석 텍스트`의 **삼단 정박 구조** 안에서만 사용한다. 이 구조가 무너진 패턴.

### N-1. 삼단 정박 붕괴(해석 생략) [S2]
- 패턴: 표 앞에 도입 문장은 있으나, 표 뒤에 해석 문장이 없이 곧바로 다음 절로 이동
- 처방: 표 뒤에 다음 중 하나를 1문장 삽입
  - 핵심 관찰: `위 [표 N]은 {핵심 요지}를 요약한다`
  - 선택 근거: `위 [표 N]에 따르면 {핵심 사실}이다`
  - 적용 범위: `앞서 [표 N]에 제시한 {대상}에 근거해, 본 사업은 {결론}을 채택한다`

### N-2. `본 표는 ... 정리함` 단순 도입 반복 [S2]
- 패턴: K-4와 동일 현상을 접합 관점에서 재분류. 메타 발화만 반복되고 표의 필요성·맥락 서술 부재
- 처방:
  ```
  [전] 본 표는 {대상}을 정리함.
       **[표 {CH}-1] {대상} 내역**
       
  [후] {대상}은 역할과 적용 범위가 서로 다르므로, 항목별
       구분하여 제시할 필요가 있다. 주요 내역은 다음과 같다.
       
       **[표 {CH}-1] {대상} 내역**
  ```

### N-3. C3 주어화 [S1]
- 패턴: `표는 ~이다` / `표의 ~은 ~` / `표에서 ~한다` — 표를 문장의 주어로 강제
- 처방: C1 예고형(`다음과 같이 ~한다`) 또는 C2 후행 약참조(`위 [표 N]은 ~을 요약한다`)로 변환

### N-4. 캡션 없는 코드펜스(그림 기근) [S2]
- 패턴: 아키텍처·흐름·상태머신을 코드블록으로만 제시하고 캡션 미부착
- 문제: md 환경에서 `캡션 없는 코드펜스`는 장르상 `코드 블록`이며, `캡션 붙은 다이어그램`과 담화 기능이 다름
- 처방: 코드펜스 위에 `[그림 {장}-{번호}] {주제} {헤드노운}` 형식 캡션 삽입. 캡션과 코드펜스 사이 빈 줄 1개. 그림 헤드노운 집합은 `caption-headnouns.md` 참조

### N-5. 표 3개 연속 + 해설 부재 [S2]
- 패턴: 한 절에 표가 3개 이상 연속 등장하면서 중간에 해설 문단 없음
- 처방: `표 1개 -> 해설 단락 -> 표 1개` 리듬 복원

### N-6. 그림 뒤 독법 안내 생략 [S2]
- 패턴: 그림만 제시하고 `상단은 ~, 중앙은 ~, 하단은 ~` 식 독법 안내 문장 부재
- 처방: 그림 직후 1문장 삽입. 독자가 그림을 본문 맥락으로 다시 접속하도록 유도

## O. 발주 규정 Hard Rule 위반 — S1

RFP·평가항목·공공기관 내부 규정에서 **명시적으로 금지**되거나 **중립 표현 권장**되는 표현. 발견 즉시 제거 또는 치환.

각 발주 사업의 hard rule은 프로젝트별로 상이할 수 있으므로, 본 카테고리는 **대부분의 공공 SI 제안서에 공통되는 규범**만 다룬다. 사업별 특수 규정은 해당 프로젝트의 `CLAUDE.md`·`제안서 작성 지침`에 별도 정의하여 proposal-style-rewriter가 로드하도록 구성.

### O-1. 모호한 표현 [S1]
- 패턴: `~할 수 있다`, `~할 수 있음`, `가능하다`, `가능함`, `고려하고 있다`, `고려 중이다`, `~을 지향한다`
- 근거: RFP 공고문에 "가능 표현은 평가 시 배점 감점 또는 0처리" 명시되는 경우가 많음
- 처방: 확정형 단정 서술로 전환
  - `높일 수 있다` -> `높인다`
  - `가능하다` -> `수행한다` / `지원한다`
  - `고려 중` -> `적용한다`(확정 시) / 해당 문장 삭제(미확정 시)
- 예외: RFP가 `설계·검토·적용검토`를 명시한 영역은 유지

### O-2. 외부 SaaS 기본값 명시 [S1] (공공기관 내부망 원칙)
- 패턴: 외부 SaaS 도구를 사업 기본 인프라로 기술
- 처방 치환 쌍:
  | 금지 | 허용 |
  |---|---|
  | Jira / Jira Risk Register | 내부 이슈관리 시스템 / 위험관리 이력 대장 |
  | Confluence | 공유 드라이브 또는 내부 문서관리시스템 |
  | Slack | 승인된 내부 알림 채널 |
  | PagerDuty | 고우선 관제 알림 체계 |
  | GitHub / GitHub Actions | 내부 Git 저장소 / 내부 CI/CD 파이프라인 |

### O-3. 클라우드 고유 서비스명 [S1]
- 패턴: 특정 퍼블릭 클라우드나 특정 오픈소스 구현체의 고유명을 본 사업 기준선으로 기술
- 처방: 중립적 역할 표현으로 치환
  - `S3 Glacier` / `Deep Archive` 등 -> `장기보관 계층`
  - 특정 GPU 인스턴스 타입 -> `고성능 GPU 노드(vCPU/메모리/GPU 스펙 명시)`
  - 특정 오브젝트 스토리지 구현체 -> `S3 호환 오브젝트 스토리지`
- 예외: 비교 대안·참고문헌 맥락에서는 고유명 허용

### O-4. 구버전 잔재 [S2]
- 패턴: 제안서 버전 개정·표준 버전 상향 이후 잔존한 구버전 표기
- 처방: grep으로 전수 탐지·치환. 사업별 기준선 버전을 `proposal-style-rewriter`에 파라미터로 전달

### O-5. 평가 전 결정 고정 [S1]
- 패턴: 발주처와의 평가·협의 이전에 특정 기술 구현체·모델명·차원 수를 사업 기준선처럼 확정 서술
- 처방: `{평가 요구사항 ID} 평가 결과와 발주처 협의 후 확정` 또는 `{평가 단계} 이후 확정할 후보` 형태로 격하

### O-6. 오픈 스펙과 벤더 SDK 혼동 [S1]
- 패턴: 오픈 스펙(프로토콜·표준)을 특정 벤더 종속 표현으로 기술
- 처방: **언어별 SDK**·**표준 구현체**로 분리 표기

### O-7. 이모지 사용 [S1]
- 패턴: 평가 문서에 이모지 포함
- 처방: ASCII 대체 — `[O]`, `[X]`, `[WARN]`, `[NOTE]`, `->`, `<-`

## 탐지 출력 스키마 (proposal-style-detector -> proposal-style-rewriter)

`humanize-korean`의 탐지 스키마(02_detection.json)와 동일 구조. 카테고리 코드만 K~O 사용.

    "severity_weighted_score": 68.3,
    "category_summary": {
      "K": 32, "L": 8, "M": 12, "N": 18, "O": 4,
      "humanize_korean_A_J": 13
    }
  },

      "category": "K-1",
      "category_label": "조달-확약 레지스터 이탈: 본 컨소시엄은 연속 노출",
      "severity": "S2",
      "text_span": "본 컨소시엄은 {REQ-ID}을 {방식}으로 구현한다.",

## 카테고리 우선순위 (윤문 적용 순서)

조달 제안서 특화 패턴이 겹칠 때 해결 순서:

1. **O (Hard Rule 위반)** — 발주 규정 직접 위반, 최우선
2. **M (캡션 형식)** — 스캐닝 평가 직접 영향
3. **L (추적성 위상)** — 의미론적 오류
4. **K (레지스터)** — 문체 일관성
5. **N (접합)** — 담화 리듬

humanize-korean A~J와 겹칠 때는 **이 proposal-style 카테고리가 우선**. 예: `할 수 있다`(A-10, S2)와 `가능하다`(O-1, S1)가 겹치면 O-1 기준으로 S1 처리.
